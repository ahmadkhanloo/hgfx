## Critical mismatch: bare defaults would benchmark **different models**

- MATLAB at this precise reference commit: `fitModel(y, u)` selects **`ehgf_binary`**, whereas released HGFX `src/hgfx/compat/fit.py::fit_model(y, u)` defaults to **`hgf_binary`** (Python verified source blob `ab58036142993757ed9144a8dd16df74dc27a832` at HGFX release `4dd8fbd8239d05f2c7932a9a9b3b7795f0a9ab27`).
- The original REV-2.3 plan explicitly says **binary HGF, default configuration** for `S128/S512`; to express the *same* classical model, use the **explicit** frozen MATLAB configuration call `fitModel(y,u,'hgf_binary_config','unitsq_sgm_config','quasinewton_optim_config')`, paired to the Python `fit_model(y,u,'hgf_binary_config','unitsq_sgm_config','quasinewton_optim_config')`. This is an *entrypoint identification*, not an executed or verified scientific parity result.
- MATLAB's optional config strings are resolved by `str2func`, and the prepared `r` includes ignored/irregular indices; do not time `hgf_binary(r,p,'trans')` against `fit_model` and call it a matched fit. Its counterpart is the **fixed-vector forward** output and must have equivalent state preparation/output materialization.
- JAX `fast_binary_hgf` uses distinct compiled `lax.scan` machinery; JAX `fit_hgf_binary_unitsq_fast` uses a **different optimizer**, and `fit_hgf_binary_unitsq_batch` takes regular, per-subject 1D binary responses/inputs. Their presence is **not** cross-backend scientific fit parity.
